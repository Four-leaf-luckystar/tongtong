# 第一部分：主题整理

## 一、阅读 App 与开源阅读书源

- 目标是在童话机中新增阅读 App，内置用户提供的开源阅读（Legado）格式书源，支持搜索、详情、目录、正文、书架和离线缓存。
- 纯前端 PWA 可以完成主要阅读流程，但第三方书源通常受到浏览器 CORS 限制，因此接受使用 Cloudflare Worker 等轻量反代。
- Legado 规则应按兼容等级处理：CSS、XPath、JSONPath、正则等基础规则优先支持；依赖 @js、登录态或 Legado 特有运行环境的高级书源，需要降级、标记不兼容或后续逐步适配。
- 建议书源、书架、阅读进度和章节缓存使用 IndexedDB；开发前仍需拿真实书源做搜索、目录和正文全链路测试。

## 二、外接长期记忆库

- 记忆库服务于童话机中的 AI 对话角色，不是阅读 App 的笔记库。目标是减少长上下文中的遗忘、混淆和错误引用，并自动召回与当前对话相关的历史信息。
- 已明确的隔离维度是 character_id + user_persona_id；不同角色、不同用户人设之间不得串记忆。用户自行配置主对话模型、API Key、URL 和模型名称。
- 早期讨论过让小模型先判断是否检索，但最终暂定每轮固定召回“最近 N 条 + top K 语义相关”，先不增加路由判断。
- 语义检索依赖 embedding：把文本转成向量，再按相似度找相关记忆。2 核 2G 学生机不适合部署 Ollama；曾讨论免费模型 API，但此方向后来被 Cloudflare 方案替代。

## 三、角色控制真实手机

- 纯网页 PWA 无法稳定控制真实手机，这是浏览器权限模型的限制。Android 需要原生 APK，并使用 AccessibilityService、UsageStats 等系统能力。
- 目标场景是角色结合用户对话和前台 App 状态采取行动，例如用户打开抖音后，角色提示“不许去”并让手机返回童话机。热门 App 做基础适配即可，不追求全机型、全应用覆盖。
- Android 可参考 Operit 的无障碍、ADB、Root 多通道思路，但项目初期宜从无障碍服务和少量热门 App 规则开始。仅用 PWABuilder 或 Bubblewrap 封装 PWA，不能自动获得这些原生控制能力。
- iOS 即使通过 TestFlight 分发，也不能像 Android 无障碍服务一样跨 App 接管系统；可考虑快捷指令、通知、深链和用户确认式快捷按钮。
- 该能力被视为未来主线，但当时网页聊天主线尚未正式打通，因此只做可行性确认，没有排入当前开发计划。

简单讲:CORS 是浏览器的**安全机制**,全名「跨源资源共享」。

## 一句话理解

你的阅读 App 网页跑在 `fairytales.app` 这种域上,书源接口在 `www.xxx-book.com` 上。浏览器默认**禁止网页去请求别人家的接口**,除非对方服务器明确说「我同意你访问」——这个「同意声明」就是 CORS 响应头。

## 加上反代后发生什么

书源服务器基本都不会主动给你加 CORS 头,所以请求会被浏览器直接拦掉。加一层 Cloudflare Worker 反代后:

- 你的 App → 请求 **你自己的 Worker**(同源,浏览器不拦)
- Worker → 请求 书源服务器(服务器之间没 CORS 限制)
- Worker 把结果**加上 CORS 头**返回给 App,浏览器的限制就满足了

所以反代的作用就一句话:**把「跨域」变成「同域」,绕开浏览器限制**。你不用关心 CORS 细节,Worker 帮你处理掉,你按我上一版提的「是否接受只支持非 `@js:` 书源、书源是否内置、Worker 谁来部署」三个点确认就行。

## 云端 vs 本地:谁更牢、更不容易记错

先纠正一个常见误解:**「牢固不牢固」不取决于云还是本地,而取决于「检索准不准」和「写入会不会重复/矛盾」**。

- 本地 IndexedDB:存在用户手机里,不联网也能读,但换设备/清缓存就没了,且数据量大了检索慢。
- 云端数据库:不丢、多设备同步、可以放专门的检索引擎,但**必须联网**,且你这是纯前端 PWA,要自己搭后端。

真正影响「记错/记乱」的是这两件事,跟放哪没关系:

1. **写入时去重 + 冲突归并**:同一个事实(「我最喜欢猫」)用户说了三遍,如果每遍都存一条,下次检索会三条全冒出来,角色就会唠叨或自相矛盾。需要在写入时判断「这条和已有记忆是不是同一件事」,是就更新而不是新增。
2. **检索时相关性排序**:角色回忆时要能把「最相关的那几条」捞出来,而不是把所有记忆都塞进上下文——塞太多正是你说「上下文一长就记错」的根因。

所以关键不是云 vs 本地,是**有没有一个好的写入归并 + 检索机制**。

## 「自动找出相关的」=需要语义检索

你要的「自动找相关」有两种实现,难度天差地别:

- **方案一:关键词/标签检索**。给每条记忆打标签、存关键词,回忆时按当前对话里的词去匹配。简单、快、可纯本地跑。缺点是不懂「语义」——用户聊「我家那只橘猫」,标签里只有「宠物」就匹配不上。
- **方案二:向量语义检索**。每条记忆转成向量(embedding),回忆时把当前对话也转向量,按相似度找最相关的几条。能懂语义、效果接近真人「联想」。但它需要:
  - 一个 embedding 模型(要查 API,纯前端跑不了大的,得用云端模型或小模型)
  - 一个向量存储 + 检索(本地可做简易版:存 IndexedDB,每次全量算相似度,数据小够用;大了就得服务端向量库)

## 给你的务实判断

**纯前端 + 本地方案**(推荐起步档):
- 记忆存 IndexedDB,写入时调用一个 LLM 做「去重/归并」(判断新事实是否和旧记忆重复或冲突),检索时也调 LLM 或用关键词。
- 优点:不加后端,符合你 PWA 调性,换设备只是丢历史(可后续加云端同步作为增强)。
- 缺点:LLM 归并/检索都要联网调 API、有成本;语义检索在端上只能做简化版。

**云端方案**:
- 记忆存云端 DB + 向量检索,App 只发请求。检索又快又准,多设备一致。
- 缺点:你不是纯前端了,要长期维护一个后端(数据库 + embedding 调用 + API 鉴权),成本和复杂度上一个台阶,和你「纯前端 PWA」的定位略冲突。

## embedding 端点是啥

embedding 就是「把文字变成一串数字向量」的能力。为什么需要它:你之前说「自动找出相关的」,靠向量相似度算最准(语义级),不是靠关键词字面匹配。 embedding 任务是把文字转向量的那个专门接口/模型。

- 很多对话模型服务(比如某些中转站、本地推理后端、部分三方代理)**只支持 chat(聊天补全),不支持 embedding**——你让它 turn-into-vector,它没这接口。
- OpenAI 官方有专门的 embedding 端点(`text-embedding-3-small` 等),是独立于 chat 的另一套 API、另一条 URL、另一种计费。

所以童话机里:用户填的那一对话 API,不一定顺手有 embedding 端点能用。这就是我上版说「若用户那家没提供 embedding 端点要怎么办」的意思——那就会缺了「语义检索」这条核心能力,只能退回关键词匹配(效果差一档)。

好消息:embedding 调用极便宜,而且很多厂家里「同家模型」一般都配了 embedding 端点(OpenAI、智谱、通义、deepseek 这类都有)。让用户在记忆库设置里**可选地**单独配一个 embedding 端点就行,**不配也能用**,只是检索退回纯关键词档。

## 路由逻辑复不复杂

我说实话:**不复杂,但麻烦,还容易吃 token**。

「路由逻辑」本质就是**:每轮对话多调一次小模型**,让它判断「这轮要不要去记忆库查」,输出 是/否。

复杂之处不在「判断本身」(那只是一次普通 LLM 调用),在**这几个隐藏坑**:

1. **判断准不准很玄**:模型可能在该查时说「不用查」,不该查时又说「要查」,你调 摆 balance 不如直接固定 recall。
2. **会丢召回**:一旦某轮被判断为「不用查」,但实际该查,角色就当场失忆,用户体感差。AI 判断是否查 + 不召回 = 失忆,这是用户体验高风险点。
3. **不省钱**:你想省「无意义查询」的钱,但每轮都要多花一次「判断」的调用,反倒**每轮都花钱**。真要省钱,应该是「能固定拿几条相关就别那么多次调用」。
4. **多写一层调试**:判断逻辑出 bug 时,你不确定是「召回没查到」还是「根本没去查」,排查链路变长。

**我的真实建议**:别上一上来就路由。先做**「固定召回」**:每轮对话固定把「最近几轮 + 与当前消息语义最相关的 top 3~5 条记忆」塞进上下文。模型自己会判断「这条memory 用不用」,不必「人来控制查不查」。这是业界 RAG 的常见做法,比你说的「AI 判断要不要查」更稳、更经济、更不容易失忆。

## 总体架构

```
用户发消息
  ↓
[1] 当前消息 → embedding(用用户配的 embedding 端点)
  ↓
[2] 检索 IndexedDB:
      - 取「当前角色 + 当前 user 人设」作用域下
      - 语义相似 top K(默认 5)
      + 最近 N 条(默认 10,按时间序)
  ↓
[3] 去重合并 → 拼进对话 prompt 的「记忆区」
  ↓
[4] 调用户配的对话模型 → 生成回复
  ↓
[5] 新事实判定:调用户配的对话模型(用同一套,避免多配)
      判断「这轮是否产生新的可记忆事实」
      是 → 归并写入(查重 + 冲突更新)
      否 → 跳过
```

不引入任何你自己的后端,**纯前端 PWA 不破**。embedding 和归并都复用用户对话模型那套配置,你零承担。

## 关键技术决策

**1. 记忆表数据结构(IndexedDB)**
```
memory: {
  id,                       // uuid
  userId,                   // user 人设隔离
  characterId,              // 角色隔离
  content,                  // 记忆文本(如「用户养了一只橘猫叫奶油」)
  type,                     // fact | preference | event | relationship
  embedding: Float32Array,  // 向量
  createdAt,
  updatedAt,
  sourceMsgId,              // 来自哪轮对话(可溯源)
  confidence                // 0~1,归并时用过几次的会累计
}
```
查询时必须带 `userId + characterId`,天然实现你说的「角色隔离 + user 人设隔离」。

**2. embedding 存储**
存在 IndexedDB 里(一条 memory 一条向量),检索时**全量拉出来在内存里算余弦相似度**。
- 起步阶段(几百到几千条)完全够用,毫秒级。
- 未来真涨到几万条,再考虑 IndexedDB 索引优化或换方案,起步别提前优化。

**3. embedding 端点(可选配置)**
- 用户在记忆库设置里**单独可选**填一个 embedding API + URL + 模型。
- 不填 → 退化到「关键词检索」:存 `content` 的分词,检索时按词频加权。效果差一档但能用,不阻断主流程。
- 填了 → 走语义检索,top K 按余弦相似度。

**4. 归并写入(去重 + 冲突)**
发一次小请求给用户配的对话模型,prompt 大致:
```
已有记忆:
- {memory_a}
- {memory_b}
这条新对话内容:{new_message}
输出的新事实:{extracted_fact}
判断:
  - 若新事实与某条已有记忆重复 → 输出 {action: "skip"}
  - 若新事实更新某条已有记忆 → 输出 {action: "update", target: "memory_a", newcontent: "..."}
  - 若是新事实 → 输出 {action: "add", content: "..."}
```
返回 JSON,前端按 action 执行。用户配置的是便宜模型时效果不稳,所以**默认关闭「自动记忆」**,用户可在设置里手动开启,避免污染记忆库。

**5. 召回拼装(防 token 爆炸)**
- 每轮最多塞 **top K=5 + 最近 N=10**,去重后实际可能 8~12 条。
- 每条精简成一行:`[偏好] 喜欢猫, 养了一只叫奶油`。
- 在对话 prompt 里加一个 `## 记忆` 区块,明确告诉模型「这些是过去的事,相关时用,无关时忽略」。
- 这是省钱的关键:**绝不把全部记忆塞进去**。

**6. 召回时机**
你说「用户发文字,AI 判断是否要查」——这一档我们**延后**,起步固定每轮召回。但加一个小优化:
- 第一轮对话(该角色 + 该 user 人设)只塞「最近 N 条」(没语义参考,或者用户刚开聊,可能没有历史)。后面轮次才启动语义召回。
- 召回用的「当前消息文本」就是用户这轮发的原文 + 上一轮角色的回复。

- 模拟点击屏幕操作其他 app
- 读其他 app 内容(短信、通讯录、微信聊天记录)

这一档是「char 真正控制手机」的核心,但**HTML/CSS/JS 没有这个权限**。这不是技术不够,是系统设计的红线。

4. **手机自动返回童话机** → 触发无障碍「按 Home」或直接跳转回你的 app

这个拆成 4 个环节:

**环节 A:从对话意图到「要拦截的 app」**
- char 回复时,前端解析「用户提到要用什么 app」,映射到一个 app 包名列表(抖音 → `com.ss.android.ugc.aweme`)。
- 这一步需要前端有一个「常见 app 名 → 包名」的映射表(用 IndexedDB 存),只处理这一步,难度低。
- 不依赖系统,纯前端可做。

**环节 B:monitor 前台 app 并触发**
- Android 原生插件在后台跑一个前台服务(Foreground Service),每秒/每两秒调一次 `UsageStatsManager` 查「当前前台 app 是哪个」。
- 检测到前台包名在「拦截名单」里 → 触发回调到前端。
- 这是核心原生工作量,但工程量可控(一个 `.java` 文件几百行)。

**环节 C:char 说那句话**
- 前端收到「检测到打开了抖音」的事件 → 自动构造一条系统消息注入对话流 → char 回复「不许去」。
- 这步你现有对话流加个「注入事件」机制即可,不属于新架构。

**环节 D:把手机拉回童话机**
- 触发一个 Capacitor 插件调用,原生端执行:**按 Home 键**(`performGlobalAction(GLOBAL_ACTION_HOME)`)、然后**启动童话机 Activity**(用 `Intent` 拉回你的 app)。
- 不需要 root、不需要悬浮窗,**无障碍 + 一个前台服务就能做到**。
- 用户体感:刷抖音的瞬间被弹回童话机,char 说「不许去」。体验就是你想要的那种。

## 关键技术难点:你要正视的真坑

这个场景的**核心卡点是「后台检测 + 弹回」能不能长期稳定跑**,有几个硬问题:

1. **Android 后台保活**:Android 8+ 严杀后台,**前台服务(Foreground Service) + 持续通知**才不容易被杀。你要接受「在童话机运行期间常驻一个通知」,这是 Android 强行的代价,不是能力进阶问题。
2. **厂商 ROM 兼容**:MIUI、ColorOS、鸿蒙、原生 Android 对无障碍 + 前台服务的**限制各异**。有些 ROM 无障碍一断电或切后台不再触发,这是长期适配的坑。你能覆盖主流 ROM 但不能保证 100%。
3. **无障碍权限恢复**:系统重启、手动停用无障碍、安全模式,都会让无障碍失效。要在 app 启动时**检测无障碍是否打开**,没打开引导用户去开。这是「日常使用」的体验损失点。
4. **用户感知是「app 突然自己跳走了」**:这会反噬安全感和信任。设计上要让 char 的回复先出来再跳,而不是无脑跳。体验设计比技术实现还重要。
5. **假锁属性:用户可以快速切回抖音**:无障碍 Home 只能把你弹出来一次,用户再点回去还能再开。要做真连续锁就得加 overlay 覆盖(中档方案),工程量加一层,但也不复杂。
6. **App 包名维护是隐性长尾**:常见 app 包名能维护一个小白名单清单(国内主流几十个),但用户提到的小众 app 不在表里就处理不到。可以加上「用户手动维护拦截列表」入口兜底。

**一、整体架构**

```
用户浏览器(童话机 PWA)
   │  每轮对话前:search_memory → 拿回相关记忆 → 拼进 prompt
   │  每轮对话后:add_memory → 把这条对话存进库
   ▼
Worker URL(用户自己的 CF Account 下)
   ├─ /add         → 写 D1 + 写 Vectorize
   ├─ /search      → 查 D1(最近 N) + 查 Vectorize(top K) → 合并去重
   ├─ /list_recent → 只查 D1(热缓存用)
   └─ /init        → 自检(给前端验证库是否就绪)
   ├─ D1 数据库(记忆原文 + 元数据,结构化查询)
   └─ Vectorize index(向量,语义检索)
```

关键点:**Worker 是用户自己的,URL+token 存在用户浏览器 IndexedDB**,你项目方不碰这条链路上任何一环。

**二、数据结构**

`D1` 里一张表 `memories`,字段:

| 字段 | 用途 |
|---|---|
| `id` | TEXT PRIMARY KEY,UUID |
| `character_id` | 哪个角色,隔离用 |
| `user_persona_id` | 哪个 user 人设,隔离用 |
| `turn_id` | 关联到哪一轮对话,可选 |
| `role` | `user` / `assistant` / `summary`(摘要) |
| `content` | 记忆原文 |
| `importance` | 0-1,可选,默认 0.5 |
| `created_at` | INTEGER,毫秒时间戳,排序用 |

`Vectorize` 里一个 index,维度跟 embedding 模型对齐(用 Workers AI 的 `@cf/baai/bge-base-en-v1.5` 或中文友好的 `bge-m3`,768 维)。Vectorize 不存原文,只存 `id` + metadata,metadata 里至少放 `character_id` 和 `user_persona_id` 做过滤。

**三、Worker 暴露的四个接口**

伪代码签名,你看逻辑就行,实际代码等你拍板开工我再写:

```
POST /add
body: { character_id, user_persona_id, role, content, importance?, turn_id? }
返回: { id, status: "ok" }
副作用:
  - INSERT 到 D1
  - 调 Workers AI 拿 embedding
  - 向量 + metadata 写 Vectorize

POST /search
body: { character_id, user_persona_id, query_text, recent_n=10, top_k=5 }
返回: { memories: [...按时间排好序的合并结果] }
逻辑:
  - D1: WHERE character_id=? AND user_persona_id=? ORDER BY created_at DESC LIMIT recent_n
  - Vectorize: top_k 语义召回,metadata 过滤同一对 id
  - 合并去重(以 id 为主键)
  - 重新按 created_at 排序返回

GET /list_recent?character_id=...&user_persona_id=...&limit=20
返回: 最近 N 条,给前端热缓存用,不走向量

GET /init
返回: { d1: true, vectorize: true, workers_ai: true }
给前端验证三件套是否就绪
```
